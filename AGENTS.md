# Quick checklist for an agent

- Read the architecture notes below (feature folders, Provider + repository pattern).
- Use `lib/src/app_providers.dart` as the canonical place for app-scoped providers.
- When changing navigation or deep links, update `lib/main.dart` and `lib/src/deeplink/DeepLinkConfig.dart` together.
- Preserve secret files and configs (see `Secrets & env` section).

# What this project is (big picture)

- Popp is a Flutter application (Android, iOS, Web) organized by feature under `lib/src/`.
- The app uses Provider (ChangeNotifier) for state, lightweight repository/viewmodel layers, and Cloud Firebase for backend services.
- Key runtime responsibilities (auth, crash reporting, remote config, messaging, deep links) are wired in `lib/main.dart`.

# Key architecture points (what to know first)

- Feature-first layout: every major feature lives under `lib/src/<feature>/` (examples: `dashboard/`, `login/`, `products/`, `services/`).
- App-wide dependency injection: `lib/src/app_providers.dart` builds the `MultiProvider` used at app root. Example: DashboardViewModel is created with `ProductRepository()` in this file.
- Navigation is centralized as helper functions in `lib/src/navigation/nav_router.dart` and routes are registered in `lib/main.dart`. The app also uses a global `navigatorKey` (see `lib/main.dart` where `navigatorKey` is declared) for programmatic navigation.
- Firebase-first backend: `lib/firebase_options.dart` (generated by FlutterFire) + `lib/src/api/firebase/*` are the single source of truth for how the app connects to Firestore, Auth, Storage, Remote Config, and Messaging. Collection names/constants live in `lib/src/api/api_url.dart`.
- Deep links: handled by `AppLinks` and parsed in `lib/main.dart`'s `_navigateToDetailScreen` (uses ApiUrl collection names), with configuration helpers in `lib/src/deeplink/DeepLinkConfig.dart`.
- Logging: follow project guideline and use `AppLogger` (see `CODING_GUIDELINES.md` and `lib/src/utils/app_loger.dart`) — avoid `print()`.

# Developer workflows and commands (concrete examples)

- Setup & run locally:
  - `flutter pub get`
  - `flutter run`
- Run tests: `flutter test` (tests live under `test/`) — basic widget tests included.
- Static analysis: `flutter analyze` (project includes `analysis_options.yaml` with `flutter_lints`).
- Build & publish (project helper): `./build_with_increment.sh` (project root) — this script:
  - cleans caches (`flutter clean` + `./gradlew clean`)
  - increments the `pubspec.yaml` build number
  - runs `flutter build appbundle --build-name=... --build-number=...`
  - runs `android/./gradlew publishReleaseBundle --track internal` (uploads to Play internal testing)
- Android manual publish: `cd android && ./gradlew publishReleaseBundle --track internal`
- iOS: open `ios/Runner.xcworkspace` in Xcode for signing / TestFlight builds.
- Web: use `flutter build web` to produce a deployable `build/web/` directory; hosting is project-specific (Firebase Hosting, Netlify, etc.). Note: `lib/firebase_options.dart` includes web `FirebaseOptions` — ensure keys and App Check (ReCaptcha) configuration are correct for web.

# Patterns & conventions to follow (project-specific)

- Provider/Repository pattern: Most viewmodels take a repository in their constructor and are registered in `AppProviders`. Example: `DashboardViewModel(ProductRepository())` in `lib/src/app_providers.dart`.
- Navigation helpers over string routes: prefer calling functions in `lib/src/navigation/nav_router.dart` (e.g., `onProductDetailsTap`) for passing typed data instead of ad-hoc `Navigator.pushNamed`.
- Deep link flow expects authenticated user: `_navigateToDetailScreen` in `lib/main.dart` checks `FirebaseAuth.instance.currentUser` and pushes `/login` if missing — keep that behavior when adding deep-linked flows.
- Firestore collection constants: use `ApiUrl` (e.g., `ApiUrl.servicePath`) rather than hardcoding collection names.
- Logging: use `AppLogger` per `CODING_GUIDELINES.md` (this is enforced by team style and appears throughout the codebase).

# Integration points & external dependencies

- Firebase (Auth, Firestore, Storage, Messaging, Crashlytics, Remote Config, App Check). The app initializes Firebase in `lib/main.dart` with `DefaultFirebaseOptions.currentPlatform` (see `lib/firebase_options.dart`).
- Push notifications: `firebase_messaging` + `flutter_local_notifications` — background handler registered in `main.dart` (`FirebaseMessaging.onBackgroundMessage`). On web, FCM requires a service worker and web credentials; `main.dart` already activates `FirebaseAppCheck` with `ReCaptchaV3Provider` when `kIsWeb` is true.
- In-app purchases via `in_app_purchase` and platform-specific packages (Android / StoreKit).
- App Links / deep linking via `app_links` and internal `DeepLinkConfig.dart`.
- Android keystores and signing artifacts are in `android/` and top-level `keystore/` — builds use Gradle tasks. Web deployments are outside the Android/iOS signing flow; check hosting docs for your target (Firebase Hosting, S3, CDN).

# Secrets & config notes (important for agents)

- `lib/firebase_options.dart` contains Firebase keys generated by the FlutterFire CLI; other platform-specific files exist under `android/app/google-services.json` and the iOS project. Treat these as sensitive: do not create new commits that expose private credentials.
- The helper script `build_with_increment.sh` modifies `pubspec.yaml` in-place to increment build numbers — be cautious when changing CI scripts.

# Where to look for examples when changing stuff

- Adding a new provider: copy pattern from `lib/src/app_providers.dart` and add `ChangeNotifierProvider(create: (_) => MyViewModel(MyRepository()))`.
- Adding a new Firestore-backed detail screen (deep link friendly): mimic `_navigateToDetailScreen` in `lib/main.dart` and use `ApiUrl.<collectionName>`.
- Adding a screen route: add a navigation helper function in `lib/src/navigation/nav_router.dart` and, when appropriate, add a named route in `lib/main.dart`'s `routes` map.

# Minimal dos/don'ts for automated edits

- DO reuse constants from `lib/src/api/api_url.dart`, `lib/src/deeplink/DeepLinkConfig.dart`, and provider registrations in `lib/src/app_providers.dart`.
- DO NOT change Firebase initialization flow in `lib/main.dart` unless you understand App Check, Crashlytics, and Remote Config impacts.
- DO run `flutter analyze` and `flutter test` after edits.
- DO NOT commit secrets or inadvertently alter `firebase_options.dart` without authorization.
